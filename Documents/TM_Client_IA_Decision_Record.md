# Task Mining Client Configuration — IA Redesign
## Decision Record & Project Log

**Project:** Redesign the Information Architecture of the Task Mining Client configuration experience.
**Team:** Product Design — Mahalakshmi Ravikumar · Product Management — Ravi Teja Avvari · UXD — Amanda Prosky.
**Timeframe:** Q2 2026. **Last updated:** 2026-07-29.

This file is a human-readable trail of the decisions made, why they were made, and what is still open. It sits alongside the working deliverables in this folder.

---

## 1. Goal & problem

Rebuild the IA of the TM Client configuration tool so that configuring **data capture** is a clear, safe, seamless journey. Research found the current experience is fragmented (a Basic web setup + an Advanced desktop editor), with unintuitive controls, confusing structure, redaction difficulties, and an OS/Windows-only dependency. Evidence that Basic is a simplified subset of Advanced: the exported Advanced config file is named `generated_from_basic_settings_*.recconf`.

## 4a. Nav ordering & the producer/consumer dependency (2026-07-15)

An alternative nav layout was proposed placing **User Attributes** and **Integrations & Extensions** *above* the Capture Rule, so that if those aren't configured, their fields wouldn't appear in the capture rule's attribute list. The reordering insight (hide irrelevant attributes to cut noise) is right, but the ordering itself was rejected: research shows the **Capture Rule is the most-used, highest-value area**, so optional features shouldn't sit above it.

The dependency is kept, but decoupled from nav order — it is **data-driven, not order-driven**:

- **Producer:** User Attributes and Integrations define the *universe of available attributes* (they "enrich the data captured by Rules" in the Object Map).
- **Consumer:** the Capture Rule's attribute list renders from whatever sources are currently enabled — reactive to configuration state, regardless of where the sections sit in the nav.
- **Default state = base attributes only.** SAP / UIAA / web-extraction / custom-attribute fields are absent until their source is enabled; enabling a source makes its fields *available* (not auto-captured — the rule still opts in per capture level).
- **Discoverability (the only real gap when sources sit below):** handled *inline* — e.g. an affordance in the rule's attribute area such as "SAP fields aren't available — enable SAP Integration" that links to the source and back. This preserves discovery without forcing setup order.

**Net:** nav order carries importance (Capture Rule near the top); conditional display carries the dependency. **To validate:** a tree-test/first-click task like "you want to also capture SAP transaction data — where do you go?" to check the inline affordance is discoverable enough.

## 5. Research findings that shaped decisions (from Ankit, Lead VE)

- **Granularity is a competitive strength** — do not reduce default capture; the fix is guidance/bucketing, not removal.
- **Redaction is "a mess"**: blanket asterisk isn't analysis-friendly, no tagging, can't handle PHI/names; wants pre-built libraries + rule testing; ordering (9-digit before 5-digit) is essential.
- **Data noise**: many fields (screenshot width/height, coordinates, heartbeat) add little value — reflected in the Low criticality ratings.
- **OS barrier**: the Advanced editor runs only on Windows; VEs on Mac must procure/emulate Windows.
