# Task Mining Client Configuration — IA Redesign
## Decision Record & Project Log

**Project:** Redesign the Information Architecture of the Task Mining Client configuration experience.
**Team:** Product Design — Mahalakshmi Ravikumar · Product Management — Ravi Teja Avvari · UXD — Amanda Prosky.
**Timeframe:** Q2 2026. **Last updated:** 2026-08-07.

This file is a human-readable trail of the decisions made, why they were made, and what is still open. It sits alongside the working deliverables in this folder.

---

## 1. Goal & problem

Rebuild the IA of the TM Client configuration tool so that configuring **data capture** is a clear, safe, seamless journey. Research found the current experience is fragmented (a Basic web setup + an Advanced desktop editor), with unintuitive controls, confusing structure, redaction difficulties, and an OS/Windows-only dependency. Evidence that Basic is a simplified subset of Advanced: the exported Advanced config file is named `generated_from_basic_settings_*.recconf`.

| 24 | **A rule's Scope is a structured condition *builder*, replacing the earlier single free-text/placeholder condition.** A scope is a tree: `[attribute] [operator] [value]` conditions combined with **AND/OR**, wrapped into **groups**, and **negated with NOT** (FR3.1–3.11). | 25 | **Advanced scope actions use progressive disclosure: NOT, Add group, and Wrap-in-group stay locked until the scope has ≥1 *complete* condition.** They render greyed with a "Complete a condition first" tooltip (not hidden) and unlock live as soon as a condition is filled. **Add condition** is always available. | Keeps the simple-first path clean (decision-tree principle in FR3.1): a user starts by naming one condition before elaborating. Negating or grouping an empty condition is meaningless and only adds validation errors. Keeping the controls visible-but-disabled preserves discoverability. | 2026-07-27 |
| 26 | **Group nesting is capped at one level.** Root level offers Add condition + Add group, and conditions there can be wrapped; **inside a nested group only Add condition is offered** (no Add group, no Wrap) — so the deepest expressible structure is `A OR (B AND C)`. NOT and delete remain available on the nested group. | Realistic scope logic for a Task Mining rule almost never needs deeper than one level of parentheses. Unlimited nesting (which FR3.6's "nestable" literally allows) produces hard-to-read trees and cognitive load for the non-engineer Admin audience. One level covers the real cases while keeping the tree shallow. Escape hatch: restructure at the root. | 2026-07-27 |
| 27 | **The IN ("is any of") operator is dropped (partially reverses FR3.8 / decision #24).** Each condition matches a *single* value; the value picker is **single-select** (choosing a suggestion replaces the field). One-value-per-condition keeps every row unambiguous and self-documenting, and OR already covers "any of." Also added a per-attribute **info-icon help tooltip** ("how to find this value", e.g. ProcessName → Windows Task Manager → Details) for when a value isn't in the suggestion list. | 2026-07-27 |
| 28 | **A condition row's secondary actions (Negate/NOT + Wrap-in-group) collapse into a single "⋯ more actions" menu; Delete stays a standalone button.** The row now shows only the three fields (attribute/operator/value) + a quiet info icon + `⋯` + delete. NOT and Wrap live in the menu (Wrap only offered on root-level rows, per #26); the `⋯` respects the progressive-disclosure lock (#25) and shows an amber tint when the row is negated. | The row had four bordered trailing controls (info, NOT, wrap, delete) plus the group's NOT — ~7 controls competing with the fields that carry the meaning. Demoting the occasional actions to a menu keeps the resting row calm and legible while preserving discoverability (one click, always visible). Delete kept outside the menu because it's the most-used and expected as a direct control. | 2026-07-27 |
| 29 | **AND/OR stays a group-level combinator (reaffirms #24); a per-row/per-connector AND/OR was considered and rejected.** All conditions in a group share one connector (AND = "all must match", OR = "any can match"); mixing is done by nesting a group (Wrap-in-group, capped at one level per #26). | A flat per-row mix ("A AND B OR C") is precedence-ambiguous and forces the engine to auto-group or apply left-to-right — hard for a non-engineer Admin to trust. Group-level combinator + explicit nesting makes the logic unambiguous and self-documenting, and matches tools stakeholders know (Gmail/Notion/Jira "match all / match any"). Raised when the user questioned whether the top toggle restricts them; clarified that many conditions are allowed and mixing is expressed via a nested group. | 2026-07-27 |
| 30 | **Scope builder switches from a top "group bar" to a stacked layout with an inline connector (Airtable/Notion pattern) — supersedes the group-bar layout of #24.** The top AND/OR segmented control + "all must match" caption are removed. The first condition reads **WHERE**; each subsequent condition carries a small inline **And/Or dropdown** on its left. The combinator remains group-level (#29) — changing any connector re-renders and flips them all together. The group's **NOT** moves to a quiet footer control ("Negate the whole scope"); **nested groups** keep a slim "Group" header holding only their NOT + delete (their own combinator still shows via inline connectors), with the one-level nesting cap (#26) intact. | Design-pattern research (react-querybuilder as the nested-tree reference; NN/g on filters; Airtable/Notion/Gmail/Intercom segment builders) showed the group-bar/tree layout is the most "engineer-flavored" of the common patterns and the heaviest on competing controls. The stacked + inline-connector layout puts the combinator where the eye already tracks (between rows), removes a whole row of chrome, and reads top-to-bottom like a list — better for the non-engineer Admin audience while preserving the exact same underlying model (#24/#26/#29). User picked this option after reviewing sentence-style (A), compact-chips (B), and stacked+connector (C) alternatives. | 2026-07-27 |
| 31 | **Negation (NOT) is removed from the scope builder entirely — supersedes the NOT provisions of #24, #25, #28 and #30.** No per-group NOT toggle, no "Negate the whole scope" footer control, no Negate item in a row's more-actions menu. Inversion is expressed by the **negative operators** (does not equal, does not contain) combined with multi-select values (#32). | With "does not equal" already an operator, a NOT wrapper expressed the same intent in two different places — and it was the control most likely to be misread by the non-engineer Admin audience, since `NOT (A AND B)` requires De Morgan's law to read correctly. Removing it collapses inversion to one obvious mechanism. **Trade-off accepted:** true group-level negation must now be hand-expanded by the Admin to `(NOT A) OR (NOT B)`; judged an acceptable loss because real Task Mining scopes rarely need it. | 2026-07-29 |
| 32 | **The condition value becomes a multi-select chip field — reverses the single-select decision of #27 and restores IN semantics without an IN operator.** Suggestions plus free typing; each committed value is a removable chip. `equals` + several values = match any; `does not equal` + several values = exclude all. Backspace on an empty input **arms** the previous chip (subtle indigo ring) rather than deleting it; a second Backspace removes it. | #27 dropped IN because a comma-separated list inside one field is opaque and hard to validate per item — chips answer exactly that objection: every value is a discrete, individually removable, individually validatable token, so the row stays self-documenting. It also removes the row explosion that single-select forced (five apps meant five OR-ed rows). Arming-before-deleting was added because immediate deletion on Backspace destroyed values the Admin could not see themselves about to lose. Reinstates FR3.8's intent through the value control rather than an operator. | 2026-07-29 |
| 33 | **Group nesting cap raised from one level to two — supersedes #26.** Root plus two nested levels. Two levels covers the realistic cases while still bounding tree depth and reading top-to-bottom. The background container communicates depth without drawing an explicit tree, which was the "engineer-flavored" quality #30 set out to avoid. | 2026-07-29 |
| 34 | **A condition row's Delete moves into the more-actions menu — reverses #28.** The `⋯` menu holds "Wrap in group" (conditional) plus "Delete condition" (always). Hence `⋯` is unconditionally enabled; only Wrap is conditional within the menu. | 2026-07-29 |
| 35 | **Operator set expanded to six and made attribute-aware — supersedes #24's three-operator list.** equals, does not equal, contains, does not contain, starts with, **Like**. "Like" is the term stakeholders already recognise from SQL, where "matches (wildcard)" was our own invented phrasing. | 2026-07-29 |
| 36 | **"Add condition" becomes a split button, with "Add group" demoted behind its caret.** At the nesting cap the caret is **hidden entirely** rather than disabled. | Add condition is the overwhelmingly common action; presenting both at equal weight implied grouping was a routine step in building a scope. Hiding the caret at max depth removes a dead-end control instead of leaving a disabled one to be puzzled over — a deliberate departure from #25's "visible but disabled preserves discoverability", which applies to *temporarily* locked actions, not permanently unavailable ones. | 2026-07-29 |
| 37 | **Low-value event families are hidden behind a disclosure and default OFF.** **Scroll** and **Session & lifecycle** become their own event families, revealed by a "Show less valuable events" link that mirrors the existing "Show rarely-used fields" pattern, and are off in Custom's default set. | Extends FR5.5's noise-hiding principle from data fields to events, which it previously did not cover. These are the highest-volume and lowest-analytical-value events, so surfacing them by default both bloated the list and invited an expensive capture setting to be switched on casually. Keeps Custom's starting set lean and privacy-safe (#21). | 2026-07-29 |
| 38 | **The Default rule's capture level becomes editable (defaults to Full), and its guarantee is restated as *coverage*, not *capture* — supersedes #16 and #17 on this point.** It still cannot be moved or deleted. A **non-blocking** amber warning appears wherever the level is set to anything other than Full. The words "catch-all" and "captures everything" are removed from Default-rule copy. | #16 and #17 fixed the level to Full on the reasoning that the Default "guarantees nothing is silently dropped" — but that guarantee only ever held *at Full*, so it was a claim about capture masquerading as a structural invariant. The genuine invariant is **coverage**: the Default always exists and always matches, so every activity is evaluated by exactly one rule *regardless of level*. Separating the two lets Admins adopt a deliberate **deny-by-default** posture (capture nothing unless explicitly scoped), which privacy-conservative customers will want. The warning is what makes a restrictive Default *deliberate rather than silent*, and must never block Save because such a configuration is legitimate. **Terminology note:** "catch-all" reads colloquially as "captures everything" and so directly contradicted that warning whenever the level was Custom or Deny — the card now states only *when* the rule applies, leaving *what it captures* to the level pill and the warning. | 2026-07-29 |
| 39 | **Rule-name validation implemented per FR2.2: required, unique case-insensitively, blocking Save.** Compared on the trimmed value against **all** rules including the Default. A new rule starts with an **empty** name and focus in the field. The **required** message appears on **blur**; a **duplicate** is flagged **live** while typing. An unnamed rule shows as "Unnamed rule" in the list in an error style. | FR2.2 had specified this from the start but it was never implemented or enforced, so blank and duplicate names saved cleanly. Starting the name empty is what makes the required-field flow real — a prefilled "New rule" both suppresses the error permanently (the field is never blank) and manufactures duplicates on a second creation. Splitting the timing avoids scolding a field the Admin has not yet touched, while still keeping a disabled Save explicable rather than mysterious. | 2026-07-29 |

| 40 | **Every create/edit flow for a *collection item* happens in a modal dialog — supersedes the page-based rule editor of #14.** One pattern across the whole app: **Capture rule**, **Redaction pattern**, **User attribute** and **Web-page extraction rule** are created and edited in a dialog using **Submit / Cancel** (FR1.6). Submit **stages** into the working config and closes; **Cancel discards** — a newly created item is **removed outright**, an existing one is **reverted from a snapshot** taken when the dialog opened. **Submit stays disabled until the item is valid.** Dialogs are **sized to their content**: a capture rule is near-fullscreen with sticky header and footer and a scrolling body (its fully expanded content measures ~2,650px, about 2.8× the viewport, with 29 toggles and 12 accordions), whereas a redaction pattern or user attribute is a conventional centred dialog. **Escape cancels; clicking the overlay does not** — on a form this size a stray backdrop click discarding a part-built item is a bad trade. **Explicitly NOT modal:** the singleton settings screens (Hashing, Consent, Data Connection, Client Behaviour, SAP Integration) stay as inline forms on their own screen, edited directly and committed by the global Save. | The page-based editor of #14 produced a **dead end**: "Create new rule" committed the rule to the list immediately, so leaving without a name stranded an invalid rule that — with delete still unbuilt (FR2.6) — could not be removed, while the global Save stayed blocked indefinitely; every mis-click added another one. Gating Submit on validity fixes that at the root instead of patching it with discard prompts or undo toasts: **an invalid item can never reach the list**, so no cleanup mechanism is needed. A dialog also closes the page flow's other hole — navigating to a different config area mid-create and stranding a half-built draft. Cancel-with-snapshot is a bonus the page flow never had: **per-item revert**, where previously every keystroke mutated the working config irreversibly. The singleton exception matters because those screens are low-touch, always-present and fully pre-filled (FR9.1, FR10.1) with nothing to "create" — wrapping them in a dialog would add ceremony without adding safety. | 2026-07-29 |

| 41 | **Destructive deletes ask first with a confirmation dialog — reverses FR2.6's toast-with-Undo.** Deleting a rule opens a small dialog naming the rule, stating that its scope and captured-data settings go with it and that the change takes effect on **Save**, with **Cancel** and a destructive **Delete rule**; Escape cancels. **No undo toast.** The same pattern covers every collection item (redaction pattern, user attribute, extraction rule), and the **Default rule has no delete affordance at all** (#38 / FR2.7). | A capture rule is a large composite object — a scope tree, a capture level and dozens of per-field selections — so a few seconds of Undo is a poor safety net for something that expensive to rebuild, and an Undo that expires silently leaves **no** recovery path. Asking first is also cheap here because deleting a rule is rare, unlike the bulk toggling elsewhere in the app where a modal would be intolerable. Consistency argument too: one delete pattern across all collection items, pairing with the single create/edit dialog pattern of #40. Trade-off accepted: a confirmation is one extra click, and it does not protect against deleting the *wrong* rule if the Admin misreads the name — hence the dialog names the rule explicitly rather than saying "this rule". | 2026-07-29 |
| 42 | **The rule-list card is stripped back to name + level badge + delete + chevron.** The **scope expression is removed** from the card, the **level badge moves directly beneath the rule name** (from the far right), and a **delete icon** sits before the chevron. The **Default rule** loses its "Default" badge — the *Fallback* heading above it already carries that — and shows its explanatory subtext **inline beside its name**, level badge beneath. | The card had accumulated four competing signals (name, scope expression, level pill, plus a warning line) and the scope expression was the least useful at list level: it truncates for anything non-trivial, restates what the editor shows properly, and pushed the level badge — the thing Admins actually scan for — out to the far edge. Name-then-level reads as a single unit top-to-bottom. Dropping the redundant "Default" badge removes a label that duplicated its own section heading. | 2026-07-29 |

| 43 | **The plain-language scope summary moves off the rule card and into the rule editor — FR3.10 is removed outright and replaced by FR3.12.** In the editor it sits beneath the condition builder, **read-only**, using the **same attribute labels as the dropdowns** plus **explicit parentheses**, and appears **only once there is more than one condition**. Incomplete conditions render as `… = …` rather than vanishing. The FR3.10 identifier is **retired, not reused** (FR3.11 is cited by FR1.6 and FR2.2, so renumbering would break references). | On the card the summary failed for the exact reason it was wanted: a 2-level scope with multi-select values does not fit a card-width line and truncates, and the card had already been stripped for the same congestion reason (#42). In the editor the calculus inverts — there is no width limit, and the summary's value *grows* with nesting, which is precisely where the stacked builder (#30) can only imply precedence rather than state it. It also doubles as a verification step before Submit, catching an AND that should have been an OR. Continuity argument as well: the current Advanced editor already exposes conditions as text, so existing Admins meet something familiar. **Read-only was chosen deliberately** — an editable expression would need a parser, syntax-error states and two-way sync with the tree, i.e. teaching a query language to a non-engineer audience, with the builder reduced to a second way of doing the same thing. Suppressing it below two conditions avoids a summary that merely restates the single row above it. | 2026-07-29 |

| 44 | **A new rule opens with Custom pre-selected — supersedes only the "a new rule has no tier preselected" clause of #17; the rest of #17 (the Full · Custom · Deny model, Full and Deny locked, Custom as the one configurable tier) stands unchanged.** The level is therefore never empty, and never a blocking field in the create dialog. | #17's reasoning was that pre-selecting a tier lets an Admin accept a capture posture they never actively chose. That risk is real for **Full** — silent over-capture — but not for **Custom**, whose default set is privacy-safe by construction (#21 / FR4.4: interaction events on, content and screenshots off). The worst case of an unnoticed Custom pre-selection is therefore **under**-capture, which is recoverable and carries no privacy exposure. Two further arguments landed after #17 was written: (a) under the validity-gated Submit of #40, "nothing selected" would make the level a **third** required field alongside name and scope, adding a blocking state for a choice that has a safe default; and (b) it would leave the "what this captures" preview empty on open — precisely the panel #23 identified as the fix for Full/Custom comprehension, so deferring it until a level is clicked works against that decision. Pre-selecting Custom keeps the preview populated from the first moment the dialog opens. **Trade-off accepted:** an Admin who ignores the level cards entirely ships a Custom rule; mitigated by the preview being immediately visible and by Custom being the safe option rather than the permissive one. | 2026-07-29 |

| 45 | **Save and Apply are decoupled: Save persists a draft, Apply pushes it to users — supersedes FR1.3's single-Save model, where saving *was* applying.** Approval is handled **outside the product**: the Admin downloads the configuration, circulates it for sign-off, and returns to Apply. Three states — working · saved draft · applied (live) — surfaced beside the page title as **Not applied** / **Draft** / **Live for all users**. ## 4a. Nav ordering & the producer/consumer dependency (2026-07-15)

An alternative nav layout was proposed placing **User Attributes** and **Integrations & Extensions** *above* the Capture Rule, so that if those aren't configured, their fields wouldn't appear in the capture rule's attribute list. The reordering insight (hide irrelevant attributes to cut noise) is right, but the ordering itself was rejected: research shows the **Capture Rule is the most-used, highest-value area**, so optional features shouldn't sit above it.

The dependency is kept, but decoupled from nav order — it is **data-driven, not order-driven**:

- **Producer:** User Attributes and Integrations define the *universe of available attributes* (they "enrich the data captured by Rules" in the Object Map).
- **Consumer:** the Capture Rule's attribute list renders from whatever sources are currently enabled — reactive to configuration state, regardless of where the sections sit in the nav.
- **Default state = base attributes only.** SAP / UIAA / web-extraction / custom-attribute fields are absent until their source is enabled; enabling a source makes its fields *available* (not auto-captured — the rule still opts in per capture level).
- **Discoverability (the only real gap when sources sit below):** handled *inline* — e.g. an affordance in the rule's attribute area such as "SAP fields aren't available — enable SAP Integration" that links to the source and back. This preserves discovery without forcing setup order.

**Net:** nav order carries importance (Capture Rule near the top); conditional display carries the dependency. **To validate:** a tree-test/first-click task like "you want to also capture SAP transaction data — where do you go?" to check the inline affordance is discoverable enough.

## 5. Research findings that shaped decisions (from Ankit, Lead VE)

- **Granularity is a competitive strength** — do not reduce default capture; the fix is guidance/bucketing, not removal.
- **Redaction is "a mess"**: blanket asterisk isn't analysis-friendly, no tagging, can't handle PHI/names; wants pre-built libraries + rule testing; ordering (9-digit before 5-digit) is essential.
- **Data noise**: many fields (screenshot width/height, coordinates, heartbeat) add little value — reflected in the Low criticality ratings.
- **OS barrier**: the Advanced editor runs only on Windows; VEs on Mac must procure/emulate Windows.
